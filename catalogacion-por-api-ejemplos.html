1. En una mirada: cuántas APIs se proponen

45endpoints bajo /partner/v1
12grupos; 11 tienen rutas
17tipos de aviso por webhook
1token, del proveedor de identidad

Cómo conté: cada método con su ruta cuenta una vez, tal como está en las tablas del §5 de la propuesta funcional (si una fila trae dos rutas, cuentan dos; POST /batches sale en §5.4 y en §5.5 y cuenta una). No cuento el token, que vive en el proveedor de identidad, ni los avisos, que son eventos que el PIM le manda al tercero y no rutas que el tercero llama. Quité las tres rutas para rotar credenciales, que la arquitectura saca de la versión 1.

3. Cada API

Paso 1POST/oauth/tokenen el proveedor de identidad

Pedir un token de 15 minutos con las credenciales del sistema. Lo da el proveedor de identidad, no la API de terceros.

Request 
POST /oauth/token
Host: {host-del-proveedor-de-identidad}
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&client_id=CLI-DEMO-01&client_secret=<client_secret>&scope=catalog.read%20suggestions.use%20proposals.write%20media.write%20products.modify%20webhooks.manage
Response 200 
{
  "access_token": "eyJ...ejemplo",
  "token_type": "Bearer",
  "expires_in": 900,
  "scope": "catalog.read suggestions.use proposals.write media.write products.modify webhooks.manage"
}

Según la arquitectura: la ruta la fija el proveedor de identidad que salga de PD-26, y el token sólo identifica al cliente y sus alcances; negocios, tiendas y estado se leen en cada llamada del registro de terceros (la propuesta funcional los metía en el token).

El PIM avisa que recibió el producto del lote. Todo aviso llega firmado (HMAC-SHA256 de «timestamp.cuerpo» con el secreto de la suscripción) y al menos una vez: el repetido se descarta por eventId y el orden lo da version.

Content-Type: application/json
X-Liverpool-Event-Id: EVT-000101
X-Liverpool-Event-Type: proposal.received
X-Liverpool-Timestamp: 1793635560
X-Liverpool-Signature: v1=ejemplo-de-firma-hmac
{
  "eventId": "EVT-000101",
  "type": "proposal.received",
  "occurredAt": "2026-11-02T16:06:00Z",
  "partnerId": "SELLER-DEMO-01",
  "business": "MKP",
  "batchId": "BATCH-000045",
  "externalRef": "DEMO-PB20",

4. ¿Está robusta? Qué le falta para quedar al centavo

Veredicto. La base es sólida y ya está escrita: una sola puerta para sistemas, límites por consumidor que fallan cerrado, idempotencia en toda escritura, resultado por producto ligado a la referencia del tercero, avisos firmados con reintentos y un feed de respaldo, versionado con convivencia y un sandbox con el mismo contrato. Lo que falta no es de diseño sino de cierre: el contrato todavía describe en palabras muchos campos (17 de las 22 fichas de arriba llevan alguno ilustrativo), no tiene un catálogo único de errores, deja abiertos algunos casos de borde y casi ningún número está medido. Siete recomendaciones bloquean el piloto, once deben quedar antes de producción y una es mejora.
