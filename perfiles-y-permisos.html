NUEVO PIM · UN SOLO SISTEMA DE USUARIOS

Unificación de usuarios, perfiles y permisos

Mismo modelo conocido: una persona tiene un perfil; el perfil habilita funciones o roles; cada función puede contener permisos concretos. Se unifican EU Catalogación y Foro sin sumar privilegios ni rediseñar el resto del PIM.

Resumen para decidir

El cambio es organizativo: dejar de administrar la misma persona y algunos perfiles en dos sistemas. No se crean agrupaciones visuales, perfiles componibles ni alcances nuevos.

Decisión propuesta: unificar los cinco perfiles híbridos que ya aparecen en ambos sistemas y convertir los dos administradores en un solo Administrador del sistema, limitado a usuarios, perfiles y permisos. Conservar los demás perfiles hasta demostrar otra equivalencia.

Fuera de alcance: inventar permisos nuevos del PIM, cambiar Auth0/Apigee, resolver cuentas técnicas, definir permisos por categoría o modificar accesos de personas reales.

Cómo funciona hoy

EU Catalogación

Persona → perfil → funciones activadas.

El administrador elige un perfil y enciende o apaga funciones para ese perfil. Proveedor y Comprador administrador sólo gestionan poblaciones acotadas. Los cinco perfiles de Foro existen también en el catálogo de EU, pero se excluyen del alta ordinaria.

Foro

Persona → perfil → función/rol → permiso.

Foro separa perfiles, funciones y permisos. Por ejemplo, Edición distingue asignar edición de realizar edición; Logística distingue entrada, salida y envío.

Medido en código, no en la configuración efectiva de un ambiente. Los inicializadores de Foro no prueban las concesiones actuales.

Cómo debe quedar

Persona única → un perfil principal → funciones/roles habilitados → permisos concretos

Buscar primero. Si la persona ya existe en EU o Foro, se concilia con Auth0; no se crea otra cuenta.
Asignar un perfil principal. Se conserva el modelo actual. Un cambio de puesto cambia el perfil; no acumula dos perfiles para obtener más permisos.
Aplicar la matriz del perfil. Las funciones se administran una vez y se muestran agrupadas por módulo: Administración, Catalogación, Foro o Logística.
Evaluar el permiso. Cuando una función tiene acciones hijas, el servidor evalúa la acción concreta: asignar edición no es editar; salida no es envío.
Suspender una vez. El estado único bloquea ambos módulos y conserva historial.

Cuentas técnicas: quedan separadas de personas y perfiles. Esta propuesta no cambia el funcionamiento de API keys.

Perfiles que sí se duplican

Éstos aparecen en ambos catálogos y el backend de Foro los trata como perfiles híbridos. Se crea una sola definición; sus permisos se comparan y concilian, nunca se suman automáticamente.

Administrador: unificación propuesta, no duplicado exacto

Catalogación administrador y Administrador de Foro resuelven administración de usuarios y funciones, pero el Administrador de Foro también trae permisos operativos en sus valores iniciales. U01 conserva sólo administración de acceso; las operaciones de producto, estudio y logística permanecen en sus perfiles responsables.

No fusionar por nombre: Pull de captura ≠ Capturista; Modelo de datos ≠ Gobierno de Datos; Comprador administrador ≠ Proveedor administrador ≠ Administrador del sistema.

Funciones, roles y permisos

Se usa el mismo modelo de los sistemas actuales. “Función” en EU y “rol” en Foro ocupan el mismo nivel administrativo. Cuando Foro ya separa acciones, esa granularidad se conserva.

El modelo de seguridad se conserva; el directorio se unifica

Auth0 → frontend → Apigee → usuario activo → perfil → función/rol → permiso → backend

Se conserva

  • Auth0 autentica a la persona.
  • Apigee valida el token y consulta el usuario.
  • El usuario tiene estado, perfil y funciones.
  • El frontend muestra sólo los módulos autorizados.

Se unifica

  • Un registro de usuario, no una copia EU y otra Foro.
  • Un perfil principal.
  • Una matriz de funciones y permisos.
  • Una suspensión para ambos módulos.

No se debe conservar como diseño

  • permitAll en los servicios de Foro.
  • Confiar sólo en una cabecera de roles.
  • Decodificar un JWT sin validar su firma.
  • API keys mezcladas con perfiles humanos.
Aclaración: corregir esas deudas técnicas no crea perfiles nuevos ni cambia esta unificación. Sólo asegura que el mismo permiso que oculta un botón también se compruebe al llamar directamente a la API.

Migración sin ampliar accesos

Exportar de cada ambiente usuarios, estado, perfil y funciones habilitadas. El código no sustituye esta extracción.
Conciliar por identidad Auth0 y revisar manualmente conflictos. No vincular sólo porque dos correos se parecen.
Aplicar los cinco cruces explícitos y U01 administrativo. Los demás perfiles conservan su origen.
Comparar permisos antes/después. Si una persona ganaría una acción, queda bloqueada hasta aprobación; no se usa unión de privilegios.
Probar permitido y denegado desde pantalla y llamada directa a API.
Retirar la réplica Foro → EU sólo después de leer el usuario desde el sistema unificado y comprobar altas, cambios y suspensiones.

Sin fecha comprometida: faltan la extracción de ambiente y ratificación de DUD-22. La publicación de esta página no modifica usuarios ni permisos.
